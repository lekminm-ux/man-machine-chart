1 หลักการ TPS ที่ระบบนี้ยึด

งานมาตรฐานของ Toyota ประกอบด้วยเอกสารหลัก 3 ใบ + เครื่องมือจัดสมดุลอีก 1 — ซึ่งตรงกับ 5 ชีตใน Excel ของโรงงานพอดี

องค์ประกอบ 3 อย่างของงานมาตรฐาน

  • Takt Time — จังหวะที่ลูกค้าต้องการ (เวลาทำงาน ÷ จำนวนที่ต้องการ)
  • Work Sequence — ลำดับการทำงานของคน 1 คนใน 1 รอบ
  • Standard WIP — งานค้างมาตรฐานขั้นต่ำที่ต้องมีเพื่อให้งานไหลได้

M2 — ความสามารถกระบวนการ (ชีต Machine Capacity Sheet)

  • Completion Time = =SUM(Basic Time : Auto Time) → เวลาคน + เวลาเครื่อง (ตัวอย่างจริง: 4.13 + 46.54 = 50.67 วินาที)
  • เวลาทำงานสุทธิต่อกะ = เวลาต่อกะ − เวลาพักเที่ยง − เวลาก่อน OT = 720 − 60 − 20 = 640 นาที = 38,400 วินาที; 2 กะ = 1,280 นาที = 76,800 วินาทีต่อวัน
    (พักเที่ยง 60 นาที + พักก่อนทำ OT 20 นาที — ยืนยันโดยผู้ใช้ 1 ส.ค. 2569 · ตั้งค่าใหม่ได้ในหน้าจอ)
  • เวลาเปลี่ยนอุปกรณ์ต่อชิ้น = เวลาที่ใช้เปลี่ยน ÷ จำนวนชิ้นที่ผลิตได้ต่อการเปลี่ยน 1 ครั้ง
  • Production Capacity ต่อกะ = เวลาทำงานสุทธิ ÷ (Completion Time + เวลาเปลี่ยนอุปกรณ์ต่อชิ้น)
  • Takt Time = เวลาทำงานสุทธิ ÷ ยอดที่ต้องผลิตต่อกะ
  • กำลังการผลิตจริงของสาย = ค่าที่ต่ำที่สุดในบรรดากระบวนการทั้งหมด (คอขวด)

Cycle Time — นิยามที่ถูกต้อง (แก้ไข 1 ส.ค. 2569)

Cycle Time = รอบของคนที่ยาวที่สุด คือเวลาที่คนคนหนึ่งใช้กว่าจะวนกลับมาเริ่มงานแรกของตัวเองใหม่ — ไม่ใช่ระยะจากซ้ายสุดถึงขวาสุดของกราฟ (กราฟแสดงแค่ shot แรกหลังเริ่มเดินเครื่อง)

รอบของคนแต่ละคน = ค่ามากกว่าระหว่าง
  ก) เวลางานของตัวเองรวมกัน (ทำงาน + เดิน + รอ)
  ข) เวลาที่ เครื่องที่คนนั้นเป็นคนโหลด หยุด

Cycle Time ของสาย = รอบที่ยาวที่สุดในบรรดาคนทั้งหมด

  • เวลาของคนใช้ ผลรวม ไม่ใช่เวลาที่งานสุดท้ายจบ — การกรอก Start Time ช้าๆ ทำให้แกนกราฟยาวขึ้น แต่คนไม่ได้ยุ่งขึ้น
  • เครื่องผูกกับคนที่โหลดมัน (แถว Auto M/C ที่อยู่ใต้งานของคนนั้น) เครื่องที่ไม่มีใครต้องรอ เช่นเครื่องบดเศษ จะไม่กำหนด Cycle Time ของสาย ไม่ว่าจะวาดอยู่ท้ายกราฟแค่ไหน
  • แถวเครื่องเริ่มนับต่อจากงานของคนที่อยู่เหนือมัน เพราะคนต้องโหลดก่อนเครื่องถึงจะทำงานได้ (เครื่อง 2 ตัวที่อยู่ใต้งานโหลดเดียวกันจึงเริ่มพร้อมกัน ไม่ต่อคิว)

Approved planning changes — 1 Aug 2026

Authorization: the current client-side Admin PIN is not acceptable as security. The next security phase must design app-managed accounts, server-side sessions, roles, API authorization, approval records, and audit logging. It must not depend on company IT, SSO, Active Directory, or a client-visible secret. No implementation begins until the bootstrap-admin and approval UX are specified.

Capacity: the target plant has two shifts. Each shift is 720 minutes gross, less 60 minutes lunch and 20 minutes before OT, giving 640 net minutes per shift. Standard capacity is shown per shift and for two shifts per day: 38,400 seconds/shift and 76,800 seconds/day. OT is excluded unless explicitly modeled later.

Chart readability requirement: the Start → End input/display area must not consume the chart viewport. It must remain compact or be collapsible, and the timeline graph must remain visibly usable beside the table. The normal layout is the compact table view plus a separate full chart view; an expanded timing/detail view must never hide or squeeze the graph out of view.

Delivery gate: after coding, Claude must inspect the actual rendered screen, test the affected workflow at the target viewport sizes, verify that the graph is visible and readable, inspect the browser console, and report the results before handoff. Passing tests/build alone is not sufficient.

Continuous Usability / No-Downtime Gate: the deployed WebApp must remain usable while improvements are being developed. Local development and Production are separate environments, but the user-facing flow is not split: after GPT review, the approved version must be committed, deployed, and verified at man-machine-chart.pages.dev. A safety feature may block only the unsafe operation; it must not unnecessarily block viewing existing charts or normal chart work. If Cloud is unavailable, show cached data for review and fail closed for writes that could overwrite Production.

Active-User Continuous Release Gate: users may be viewing or editing charts during every future change. Ship only a reviewable GPT-approved commit, preserve the last known-good deployment as the rollback target, and keep UI/API/saved-chart JSON backward-compatible. Schema changes require a separately approved expand/compatibility/contract plan; do not mix ad-hoc ALTER TABLE, reset, seed, or bulk repair with an ordinary release. If a release is unhealthy, keep existing charts readable, fail closed for unsafe writes, and roll back the application without repairing live data. Do not claim safe concurrent editing until server-side authentication, authorization, audit identity, optimistic version checks, and conflict handling are implemented and reviewed; Admin PIN alone is not enough.

Save-to-Cloud Persistence Gate: the Save button is successful only after the deployed API explicitly confirms the exact chart write with a server version/timestamp. Every save-related change and release must save a uniquely identifiable edit, read it back through the deployed API, compare all metadata and step/timeline values, then refresh or reopen the WebApp and confirm the same data remains in Cloud. Local state, localStorage, fixtures, local D1, or a passing build/deploy are not proof. Ambiguous saves must remain unconfirmed, preserve work for retry, block unsafe overwrite, and never replace Cloud data with an empty or stale fallback.

Database Safety / Data Preservation Gate: Production D1 behind man-machine-chart.pages.dev is the canonical source of truth. Local Pages Dev at 127.0.0.1:8788, Next dev/localStorage, and .wrangler/ are separate test/cache environments. Never delete or recreate local D1 state to make a test convenient, and never use a one-folder sample as a restoration.

Hierarchy preservation: every folders row, parentId relationship, existing four-level tree, chart_files row, and chart content must survive persistence, schema, API, and deployment work. Before any authorized write, export Production rows/schema to a timestamped directory outside the repository. Compare before/after folder count, root count, maximum depth, complete parent-child mapping, chart count, representative IDs, and content checksums. Any unexpected decrease is a STOP condition.

Fail-closed rule: if a cloud read fails or the recovery export cannot be verified, block save/destructive actions and return DATA_SAFETY_BLOCKED. A passing test, lint, build, or deploy command is not evidence that data was preserved. The canonical detailed rules are in docs/AI_PROMPTS/DATABASE_SAFETY_GATE.md.

Verified snapshot on 2 Aug 2026: Production export contains 5 folder rows, 3 root folders, 6 chart files, and maximum folder nesting depth 3 (PD6 → BlowMold → BYD). If the UI counts the chart file as a fourth visible layer, that layer is also preserved. The export is evidence of the current state, not a seed or schema source.

Schema drift: live Production folders has parentId appended without a self-referencing foreign key, while schema.sql declares that foreign key. Do not run schema.sql, ALTER TABLE, reset, or migration against Production in Phase 0B. Any normalization requires a separate GPT plan, rehearsal, and explicit authorization.

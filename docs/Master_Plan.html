1 หลักการ TPS ที่ระบบนี้ยึด

งานมาตรฐานของ Toyota ประกอบด้วยเอกสารหลัก 3 ใบ + เครื่องมือจัดสมดุลอีก 1 — ซึ่งตรงกับ 5 ชีตใน Excel ของโรงงานพอดี

องค์ประกอบ 3 อย่างของงานมาตรฐาน

  • Takt Time — จังหวะที่ลูกค้าต้องการ (เวลาทำงาน ÷ จำนวนที่ต้องการ)
  • Work Sequence — ลำดับการทำงานของคน 1 คนใน 1 รอบ
  • Standard WIP — งานค้างมาตรฐานขั้นต่ำที่ต้องมีเพื่อให้งานไหลได้

M1 — ตารางจับเวลา (ชีต JOB_C CAP_1 แถว 8–45)

ค่าสูตรใน Excelความหมาย
Min.=MIN(C8:G8)รอบที่เร็วที่สุด → ใช้เป็น ค่าฐานส่งต่อให้โมดูลอื่น
Max.=MAX(C8:G8)รอบที่ช้าที่สุด

กฎที่ห้ามพลาด: เวลาเครื่องจักรทำงานอัตโนมัติไม่นับเป็นภาระงานของคน ทุกแถวจึงต้องระบุประเภทได้ว่าเป็น คน / เครื่อง / เดิน — ซึ่งตรงกับคอลัมน์ คน | เครื่อง | เดิน ในชีต std.com table และเป็นข้อมูลที่ M3 ต้องใช้พอดี

M2 — ความสามารถกระบวนการ (ชีต Machine Capacity Sheet)

  • Completion Time = =SUM(Basic Time : Auto Time) → เวลาคน + เวลาเครื่อง (ตัวอย่างจริง: 4.13 + 46.54 = 50.67 วินาที)
  • เวลาทำงานสุทธิต่อกะ = เวลาต่อกะ − เวลาพัก = 540 − 80 = 460 นาที = 27,600 วินาที
    (พักเที่ยง 60 นาที + พักก่อนทำ OT 20 นาที — ยืนยันโดยผู้ใช้ 1 ส.ค. 2569 · ตั้งค่าใหม่ได้ในหน้าจอ)
  • เวลาเปลี่ยนอุปกรณ์ต่อชิ้น = เวลาที่ใช้เปลี่ยน ÷ จำนวนชิ้นที่ผลิตได้ต่อการเปลี่ยน 1 ครั้ง
  • Production Capacity ต่อกะ = เวลาทำงานสุทธิ ÷ (Completion Time + เวลาเปลี่ยนอุปกรณ์ต่อชิ้น)
  • Takt Time = เวลาทำงานสุทธิ ÷ ยอดที่ต้องผลิตต่อกะ
  • กำลังการผลิตจริงของสาย = ค่าที่ต่ำที่สุดในบรรดากระบวนการทั้งหมด (คอขวด)

เรื่องสูตร =39*8.66 ในไฟล์ Excel — ตัดสินใจแล้ว (1 ส.ค. 2569): ตัวเลขนี้ให้ผล 337.74 ซึ่งไม่สอดคล้องกับ Completion Time 50.67 วินาทีในแถวเดียวกัน ไม่ว่าจะแทนค่าเวลากะแบบใด จึงถือเป็นตัวเลขที่พิมพ์ทับไว้ ไม่ใช่สูตรที่ใช้งานได้ ผู้ใช้ยืนยันให้ ใช้สูตรมาตรฐาน TPS แทน ระบบจึงไม่ทำซ้ำเลข 337.74

M3 — ตารางงานมาตรฐานผสม (ชีต std.com table)

  • คอลัมน์ต่อแถว: คน (E) · เครื่อง (F) · เดิน (G)
  • เวลาเริ่มของแถวถัดไป = เวลาเริ่มเดิม + เวลาคน + เวลาเดินของแถวก่อน (=H11+G11+E11) → เป็นการไล่เวลาสะสมแบบต่อเนื่อง
  • เส้นแดง = Takt Time · เส้นน้ำเงิน = Cycle Time
  • Rule 1: เครื่องล้นเกิน Takt → ตัดจบแล้ววนกลับเริ่มที่ 0 ในบรรทัดเดิม
  • Rule 2: Cycle < Takt → แสดงลูกศรรอ พร้อมตัวเลขวินาทีที่ต้องรอ
  • Rule 3: เครื่อง 2 เครื่องเริ่มพร้อมกัน → วาดเส้นคู่ขนาน ไม่ให้ทับกัน

ตัวเลขที่กรอกในช่อง Manual / Machine / Walk / Idle คือระยะเวลาของขั้นตอนนั้นตรงๆ

  • Count (s) = เวลารวมของแถว และเป็นตัวที่ใช้คำนวณ Cycle Time
    แถวคน = manual + walk + idle · แถวเครื่อง = machine
  • เพิ่มคอลัมน์ Start → End บอกว่าขั้นตอนนั้นอยู่ช่วงไหนบนไทม์ไลน์
  • บนกราฟมีตัวเลขกำกับทุกแท่ง (ระยะเวลากลางแท่ง · เวลาเริ่ม-จบที่หัวท้าย)

ตัวเลขเดิมไม่ถูกแปลง (ผู้ใช้เลือกทางเลือก B เพื่อให้ทีมงานเข้าใจง่าย) — ค่าที่กรอกไว้แบบยอดสะสมจึงกลายเป็นระยะเวลาทันที ต้องไล่กรอกใหม่ให้ตรงกับเวลาจริง หรือกด “ดึงข้อมูลจาก M1” มาทับ

Cycle Time — นิยามที่ถูกต้อง (แก้ไข 1 ส.ค. 2569)

Cycle Time = รอบของคนที่ยาวที่สุด คือเวลาที่คนคนหนึ่งใช้กว่าจะวนกลับมาเริ่มงานแรกของตัวเองใหม่ — ไม่ใช่ระยะจากซ้ายสุดถึงขวาสุดของกราฟ (กราฟแสดงแค่ shot แรกหลังเริ่มเดินเครื่อง)

รอบของคนแต่ละคน = ค่ามากกว่าระหว่าง
  ก) เวลางานของตัวเองรวมกัน (ทำงาน + เดิน + รอ)
  ข) เวลาที่ เครื่องที่คนนั้นเป็นคนโหลด หยุด

Cycle Time ของสาย = รอบที่ยาวที่สุดในบรรดาคนทั้งหมด

  • เวลาของคนใช้ ผลรวม ไม่ใช่เวลาที่งานสุดท้ายจบ — การกรอก Start Time ช้าๆ ทำให้แกนกราฟยาวขึ้น แต่คนไม่ได้ยุ่งขึ้น
  • เครื่องผูกกับคนที่โหลดมัน (แถว Auto M/C ที่อยู่ใต้งานของคนนั้น) เครื่องที่ไม่มีใครต้องรอ เช่นเครื่องบดเศษ จะไม่กำหนด Cycle Time ของสาย ไม่ว่าจะวาดอยู่ท้ายกราฟแค่ไหน
  • แถวเครื่องเริ่มนับต่อจากงานของคนที่อยู่เหนือมัน เพราะคนต้องโหลดก่อนเครื่องถึงจะทำงานได้ (เครื่อง 2 ตัวที่อยู่ใต้งานโหลดเดียวกันจึงเริ่มพร้อมกัน ไม่ต่อคิว)

ตรวจกับข้อมูลจริง BYD Side Step Rev.00: Worker A ทำงานของตัวเองรวม 347 วิ · Blow molding เริ่มตอน 62 (หลังโหลดเสร็จ) ทำงาน 388 วิ หยุดที่ 450 · Worker A จึงรอเครื่อง 103 วิ แล้วเริ่มรอบใหม่ที่ 450
→ CT = 450 กำหนดโดย Worker A ✅ (ระบบแสดงชื่อคนที่กำหนดรอบให้เห็นบนป้ายแล้ว)

ประวัติความเข้าใจผิด 2 รอบ:

รอบแรกระบบตอบ 385 (นับแค่เวลาเครื่องทำงาน ไม่นับว่าเครื่องเริ่มตอนไหน) · รอบสองแก้เป็น "เวลาที่เครื่องหยุด" แต่ยังผิดเพราะเอาเครื่องตัวไหนก็ได้มาคิด ทำให้เครื่องบดเศษของ Worker D ไปกำหนดรอบของทั้งสาย · ตอนนี้แก้ให้ผูกเครื่องกับคนที่โหลดแล้ว

9 กติกาการทำงานของแผนนี้

กฎเหล็ก: ห้ามอัปเดตแผนแม่บทฉบับนี้ก่อนที่โค้ดจะผ่านการทดสอบจริง

ลำดับที่ต้องทำทุกครั้งที่แก้โค้ด — ห้ามข้ามข้อไหนแม้จะเป็นการแก้เล็กน้อย:

  1. แก้โค้ด
  2. Debug จริง — npm test ผ่าน · npm run build ผ่าน · เปิด dev server ทดสอบหน้าจอจริงและอ่าน console ว่าไม่มี error
  3. ทวนสอบตัวเลข — ถ้าแตะเรื่องเวลา/ยอดรวม/สะพานเชื่อมโมดูล ต้องเช็คว่าตัวเลขใน M1, M4, M5 ยังตรงกัน
  4. ถ้าทดสอบไม่ผ่าน → แก้ให้ผ่านก่อน ห้ามข้ามไปขั้นถัดไป
  5. Deploy ขึ้น production (ดูกล่องแดงด้านล่าง) แล้วเปิดเว็บจริงตรวจซ้ำ
  6. อัปเดตแผนนี้ (สถานะโมดูล · Roadmap · Change Log ท้ายเอกสาร)
  7. อัปเดต CHANGELOG_AI.md
  8. git commit + git push

ทำไมข้อ 5 ถึงสำคัญ: พี่เห็นแค่เว็บที่ deploy แล้ว งานที่ commit แต่ไม่ได้ deploy จะดูเหมือน "ไม่มีอะไรเกิดขึ้น" — เคยเกิดมาแล้วกับ Phase 1

⚠️ Deploy ขึ้นเว็บจริงต้องสั่งเอง — git push อย่างเดียวไม่พอ

ตรวจแล้วเมื่อ 1 ส.ค. 2569: push ขึ้น GitHub แล้วรอ 13 ชั่วโมง Cloudflare Pages ไม่ได้ build ให้เลย (ไม่มี deployment ใหม่เกิดขึ้น) แปลว่า Git integration ไม่ได้เปิดใช้หรือ build ฝั่ง Cloudflare ล้มเหลว

จนกว่าจะแก้ที่ Cloudflare Dashboard ทุกครั้งที่จบงานต้องสั่ง deploy เองแบบนี้:

npm run build แล้วตามด้วย
npx wrangler pages deploy out --project-name=man-machine-chart --branch=main --commit-dirty=true

แล้วตรวจซ้ำที่เว็บจริงเสมอว่าบันเดิลใหม่ขึ้นแล้ว อย่าถือว่า deploy สำเร็จเพราะคำสั่งไม่ error
